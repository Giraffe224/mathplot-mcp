# 代码评估与优化计划 — 2026-08-21

> 对 `mathplot_mcp.py` v1.5.0（约 1500 行）的稳健性 / 可读性 / 优雅性评估结论与
> 后续优化 backlog。
> **P0+P1+P2 已于 2026-08-21 在 v1.6.0 实施并全量回归（见 CHANGELOG v1.6.0）；
> P3 推迟单独做。** 以下各节标注实施状态。

## 总评

| 维度 | 评分 | 一句话 |
| --- | --- | --- |
| 稳健性 | B+ | 单文件 stdlib 服务器里属上乘，但有隐藏并发软肋和资源管理缺口 |
| 可读性 | A- | 命名清晰、分区注释到位；每个非显然决策都写了"为什么" |
| 优雅 | B | 有刻意的务实优雅（零框架依赖），被三处重复注册和死代码拖累 |

**最大优点**：注释记录决策依据而非行为复述（image_url 报错原因、奈奎斯特老 API
陷阱、GET 405 与 RikkaHub give-up bug 的因果）——半年后救命的注释。

**最大结构性风险**：工具三处注册（schema 列表 / 名字元组 / 分发表）+ schema 与
函数签名手工同步——已实际踩过坑（`x_label` 参数不存在）。

## 不建议动的

- **单文件结构**：1500 行已到边界，但"一条 adb push 完成部署"是真实运维优势。
- **纯 stdlib HTTP**：有文档记录的刻意取舍（Termux 免 Rust 编译）。
- **safe_parse 黑名单+白名单双层防护**：对个人本地服务足够，勿过度加固。

## 本轮顺手修复（已提交部署，不属于 backlog）

- `contextlib.suppress((TypeError, ValueError))` 双括号 bug（v1.5.0 批量改写
  ast.unparse 元组时引入）：嵌套元组令 `__exit__` 的 issubclass 校验抛 TypeError，
  异常吞不掉反而爆新错误。`plot_step_response` 稳态值/超调量计算受影响。
  已修复并回归验证（ζ=0.316 理论超调 35.1% vs 实测 35.09%）。commit `e6c4164`。
- `matplotlib.use("Agg")` 之后的 import 加 `# noqa: E402`（字体配置必须先于 pyplot）。
